# Зафиксированные требования AdamLife 2.0

Статус: основа схемы и авторизация реализованы; HTTP-функции финансов и импорт
**не реализованы**. React подключён к API авторизации. Flutter и SwiftUI не изменены.

## 1. Начальный остаток и исторические операции

`opening_balance_minor` — остаток **непосредственно перед началом** даты `opening_date`
в часовом поясе пользователя. В расчёт входят операции с `occurred_on >= opening_date`.
Операция в первый день учитывается ровно один раз. Текущее значение баланса не хранится:
это начальный остаток + входящие суммы − исходящие суммы по этому счёту до выбранной даты,
без мягко удалённых операций. Будущие операции не меняют баланс «на сегодня».

Пример: на начало 1 октября 100 000 ₸, расход 1 октября 5 000 ₸ → 95 000 ₸.
Сентябрьская выписка уже включена в начальные 100 000 ₸ и не может просто прибавиться к учёту.

Будущий импорт должен показывать операции до границы отдельно и не подтверждать их как
финансовые проводки. Можно либо оставить их вне учёта, либо **явно** перенести границу назад
и установить подтверждённый остаток на новую дату. Затем импортировать подходящие строки
атомарно с проверкой дублей. Нельзя молча сдвинуть дату или прибавить всю выписку поверх остатка.
Сам остаток — не доход и не отдельная импортируемая банковская операция.

В БД уже есть защита: операция до границы отклоняется; перенос границы вперёд не может
исключить записанные операции (в том числе мягко удалённые). Проверка блокирует соответствующие
счета, чтобы не пропустить конфликт с параллельным изменением границы. Индексы поддерживают
поиск истории по владельцу/счёту. Реальный импорт и его дедупликация будут отдельным этапом.

## 2. Денежная точность и валюты

KZT, USD, EUR — отдельные валюты, по 2 десятичных знака. Хранение сумм: `BIGINT` в тиынах/центах,
арифметика Python: `int`; не `float` и не PostgreSQL `money`. При подключении API суммы передавать
десятичными строками целых minor units, чтобы JavaScript не потерял точность за пределами 2^53−1.

Валюта принадлежит счёту и после создания неизменна. Связи операции проверяют владельца,
счёт **и валюту**. Сводка возвращает суммы по кодам валют, не одно смешанное число.
Перевод внутри одной валюты имеет равные суммы обеих сторон. Межвалютный перевод хранит
две явно заданные фактические суммы. Автокурсы, скрытая конвертация и общий баланс разных валют
не добавляются. Реализация расчётов и API сумм — следующий финансовый этап.

## 3. Несколько счетов одного банка

Банк — необязательный неуникальный `bank_code`; идентификатор счёта — UUID.
Нет уникальности «пользователь + банк». Один владелец может иметь несколько счетов Kaspi,
Freedom или другого банка, в одинаковых или разных валютах. Прототипные ID `kaspi/freedom/cash`
не переносятся как серверная схема.

## 4. Безопасная корректировка начального остатка

В схеме есть версия счёта и append-only аудит. Триггер изменения остатка/даты требует
`NEW.version = OLD.version + 1` и в той же транзакции записывает старые и новые значения.
Денежные значения в JSON аудита — строки. При откате изменения откатывается и аудит.
Неизменяемость аудита обеспечивают RLS и триггер запрета UPDATE/DELETE.

Будущий сервис дополнительно должен:

1. Запросить подтверждение пользователя с причиной корректировки.
2. Заблокировать счёт и проверить `expected_version`; при устаревшей версии вернуть 409.
3. Проверить новый остаток/дату и согласованность уже импортированной истории.
4. Изменить дату и остаток атомарно, пересчитать производную сводку, вернуть новое состояние.

Кэш баланса пока отсутствует, значит нет второго несогласованного источника остатков.
CRUD и пользовательский сценарий корректировки на этом этапе намеренно не создаются.
Удаление связанных счетов ограничено FK RESTRICT; будущий сервис разрешит удаление только
неиспользованного счёта с нулевым начальным остатком. Во всех остальных случаях — архивирование.

## 5. Изоляция и авторизация

Все пользовательские таблицы включают RLS с FORCE. Без транзакционного `app.user_id` нет
доступных строк; составные FK исключают ссылки между владельцами. Контекст задаётся только
внутренним `authenticated_session()` после серверной проверки сессии. Нельзя брать user_id из
заголовка, query/body, localStorage или параметров, присланных браузером.
SET LOCAL не переживает транзакцию и не должен утекать через пул соединений.

API подключается отдельной ролью без ownership/SUPERUSER/BYPASSRLS и без членства в роли
миграций. Миграции — отдельная owner-роль. `/health/ready` отклоняет явно привилегированную
runtime-роль и неверную ревизию. Это защита в глубину, не замена авторизации.
Google lookup/bootstrap реализован узкими политиками users по проверенному sub.
Сессии и одноразовые flows имеют собственный FORCE RLS по хешу предъявленного cookie.
Подробный контракт и ограничения: [authentication.md](authentication.md).

Google OAuth реализован и проверен автоматически; до финансовых API остаётся внешняя проверка:
физический iPhone, Safari и запуск с домашнего экрана, настоящий HTTPS, redirect URI,
state/nonce/PKCE, Secure HttpOnly cookie, вход/выход, восстановление/истечение сессии.
Выбран один browser origin: frontend и /api reverse proxy к backend, чтобы
не опираться на сторонние cookie iOS. Localhost/HTTP не считается проверкой Google на iPhone.
Аккаунты, домены, Google credentials и платные сервисы без отдельного разрешения не создаются.

## 6. Обязательства и границы этапа

Расписание и конкретные платежи разделены. Пара «расписание + период» уникальна. У оплаченного
платежа есть одна связанная реальная расходная операция с тем же владельцем, счётом, валютой и
суммой; один расход нельзя привязать повторно. Просроченность вычисляется по дате/часовому поясу,
а не сохраняется устаревающим флагом. Просрочено — подмножество «осталось», а не отдельное слагаемое.
Генерация повторений, защита связанных расходов от мягкого удаления и пользовательские статусы
будут проверены в соответствующем функциональном этапе; сейчас созданы только таблицы/ограничения.

Таблицы auth_sessions/login_flows добавлены миграцией 0003_auth. import_batches/import_rows,
внешние банковские ID и правила категоризации будут добавлены с реализацией импорта.
Нет фоновых очередей, облака, сервера PDF, ИИ, финансового CRUD или аналитических endpoints.
Демонстрационные данные не переносятся в БД и не подставляются в серверные аккаунты.
