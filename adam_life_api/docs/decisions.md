# Зафиксированные требования AdamLife 2.0

Статус на 2026-11-05: авторизация и финансовый CRUD реализованы; React подключён к ним.
Импорт, расширенная аналитика и платежные сервисы не реализованы. Flutter и SwiftUI не изменены.

## 1. Начальный остаток и исторические операции

`opening_balance_minor` — остаток **непосредственно перед началом** даты `opening_date`
в часовом поясе пользователя. В расчёт входят операции с `occurred_on >= opening_date`.
Операция в первый день учитывается ровно один раз. Текущее значение баланса не хранится:
это начальный остаток + входящие суммы − исходящие суммы по этому счёту до выбранной даты,
без мягко удалённых операций. Будущие операции не меняют баланс «на сегодня».

Пример: на начало 1 октября 100 000 ₸, расход 1 октября 5 000 ₸ → 95 000 ₸.
Сентябрьская выписка уже включена в начальные 100 000 ₸ и не может просто прибавиться к учёту.

Будущий импорт должен показывать операции до границы отдельно и не подтверждать их как
финансовые проводки. Можно либо оставить их вне учёта, либо **явно** перенести границу назад
и установить подтверждённый остаток на новую дату. Затем импортировать подходящие строки
атомарно с проверкой дублей. Нельзя молча сдвинуть дату или прибавить всю выписку поверх остатка.
Сам остаток — не доход и не отдельная импортируемая банковская операция.

В БД уже есть защита: операция до границы отклоняется; перенос границы вперёд не может
исключить записанные операции (в том числе мягко удалённые). Проверка блокирует соответствующие
счета, чтобы не пропустить конфликт с параллельным изменением границы. Индексы поддерживают
поиск истории по владельцу/счёту. Реальный импорт и его дедупликация будут отдельным этапом.

## 2. Денежная точность и валюты

KZT, USD, EUR — отдельные валюты, по 2 десятичных знака. Хранение сумм: `BIGINT` в тиынах/центах,
арифметика Python: `int`; не `float` и не PostgreSQL `money`. При подключении API суммы передавать
десятичными строками целых minor units, чтобы JavaScript не потерял точность за пределами 2^53−1.

Валюта принадлежит счёту и после создания неизменна. Связи операции проверяют владельца,
счёт **и валюту**. Сводка возвращает суммы по кодам валют, не одно смешанное число.
Перевод внутри одной валюты имеет равные суммы обеих сторон. Межвалютный перевод хранит
две явно заданные фактические суммы. Автокурсы, скрытая конвертация и общий баланс разных валют
не добавляются. Текущий API разрешает только переводы в одной валюте; межвалютный сценарий отложен.

## 3. Несколько счетов одного банка

Банк — необязательный неуникальный `bank_code`; идентификатор счёта — UUID.
Нет уникальности «пользователь + банк». Один владелец может иметь несколько счетов Kaspi,
Freedom или другого банка, в одинаковых или разных валютах. Прототипные ID `kaspi/freedom/cash`
не переносятся как серверная схема.

## 4. Безопасная корректировка начального остатка

В схеме есть версия счёта и append-only аудит. Триггер изменения остатка/даты требует
`NEW.version = OLD.version + 1` и в той же транзакции записывает старые и новые значения.
Денежные значения в JSON аудита — строки. При откате изменения откатывается и аудит.
Неизменяемость аудита обеспечивают RLS и триггер запрета UPDATE/DELETE.

Финансовый сервис выполняет:

1. Запросить подтверждение пользователя с причиной корректировки.
2. Заблокировать счёт и проверить `expected_version`; при устаревшей версии вернуть 409.
3. Проверить новый остаток/дату и согласованность уже импортированной истории.
4. Изменить дату и остаток атомарно, пересчитать производную сводку, вернуть новое состояние.

Кэш баланса пока отсутствует, значит нет второго несогласованного источника остатков.
CRUD и пользовательский сценарий корректировки реализованы. Удаление связанных счетов
ограничено FK RESTRICT. По актуальному ТЗ счёт без истории можно удалить и с ненулевым
начальным остатком: UI предупреждает об исключении остатка из общего баланса.
Счета с историей, включая мягко удалённые операции, можно только архивировать.

## 5. Изоляция и авторизация

Все пользовательские таблицы включают RLS с FORCE. Без транзакционного `app.user_id` нет
доступных строк; составные FK исключают ссылки между владельцами. Контекст задаётся только
внутренним `authenticated_session()` после серверной проверки сессии. Нельзя брать user_id из
заголовка, query/body, localStorage или параметров, присланных браузером.
SET LOCAL не переживает транзакцию и не должен утекать через пул соединений.

API подключается отдельной ролью без ownership/SUPERUSER/BYPASSRLS и без членства в роли
миграций. Миграции — отдельная owner-роль. `/health/ready` отклоняет явно привилегированную
runtime-роль и неверную ревизию. Это защита в глубину, не замена авторизации.
Google lookup/bootstrap реализован узкими политиками users по проверенному sub.
Сессии и одноразовые flows имеют собственный FORCE RLS по хешу предъявленного cookie.
Подробный контракт и ограничения: [authentication.md](authentication.md).

Google OAuth реализован и проверен автоматически; до финансовых API остаётся внешняя проверка:
физический iPhone, Safari и запуск с домашнего экрана, настоящий HTTPS, redirect URI,
state/nonce/PKCE, Secure HttpOnly cookie, вход/выход, восстановление/истечение сессии.
Выбран один browser origin: frontend и /api reverse proxy к backend, чтобы
не опираться на сторонние cookie iOS. Localhost/HTTP не считается проверкой Google на iPhone.
Аккаунты, домены, Google credentials и платные сервисы без отдельного разрешения не создаются.

## 6. Обязательства и границы этапа

Расписание и конкретные платежи разделены. Пара «расписание + период» уникальна. У оплаченного
платежа есть одна связанная реальная расходная операция с тем же владельцем, счётом, валютой и
суммой; один расход нельзя привязать повторно. Просроченность вычисляется по дате/часовому поясу,
а не сохраняется устаревающим флагом. Просрочено — подмножество «осталось», а не отдельное слагаемое.
Генерация повторений, защита связанных расходов от мягкого удаления и пользовательские статусы
будут проверены в соответствующем функциональном этапе; сейчас созданы только таблицы/ограничения.

Таблицы auth_sessions/login_flows добавлены миграцией 0003_auth. import_batches/import_rows,
внешние банковские ID и правила категоризации будут добавлены с реализацией импорта.
Нет фоновых очередей, сервера PDF, ИИ или аналитических endpoints.
Демонстрационные данные не переносятся в БД и не подставляются в серверные аккаунты.

## 7. Финансовый вертикальный срез — 2026-11-05

`/finance/bootstrap`, `/finance/snapshot`, POST/PUT/DELETE accounts/categories/operations.
На frontend пути начинаются с `/api/finance`. Сессия определяет владельца; RLS и CSRF
обязательны. Изменения одного пользователя сериализуются блокировкой его строки users;
версии защищают от перезаписи устаревшими формами. Другие пользователи имеют отдельные блокировки.
Один перевод — одна строка Transaction с двумя сторонами, без дохода/расхода.
Изменение типа, суммы, счетов и мягкое удаление пересчитывают остатки из истории.
API возвращает minor units строками, React считает через BigInt. Snapshot включает `as_of`
в часовом поясе пользователя. Будущие операции и будущие начальные остатки не входят
в текущий баланс. Архивирование не скрывает деньги из общего баланса.

Миграция `0004_finance` только разрешает тип deposit; таблицы, RLS и триггеры сохраняются.
Ставка, разновидность и срок добавлены следующим небольшим этапом (0005_deposit, см. ниже).
Проценты банка доступны как обычный доход.
Удаление используемой категории запрещено: доступна архивация; расходная «Другое» защищена.
Связанные с обязательными платежами операции пока запрещено редактировать/удалять через общий API.
Серверные данные находятся только в памяти React до выхода; деморежим использует прежний отдельный клиент.
При сетевой неопределённости запись не повторяется автоматически: нужно обновить историю.
Серверная идемпотентность запросов пока не включена; пагинация истории также отложена.

## 8. Параметры депозитов

В accounts: deposit_type (savings/term), annual_rate NUMERIC(9,4), deposit_opened_on,
deposit_ends_on. Ставка — десятичная строка в API, не float. Это справочные параметры:
автоматического начисления и банковских ограничений нет. Даты и ставка необязательны
для обоих типов. Если обе даты заданы, окончание не раньше открытия.
Дата открытия не меняет учётную границу opening_date и не ограничивает переводы.

Legacy строки сохраняют NULL без выдуманной разновидности; новая форма обязательно
предлагает выбрать тип (по умолчанию накопительный). Для старого клиента, создающего
депозит без новых полей, API применяет savings. Пропущенные поля в PUT сохраняются,
явный null очищает необязательные значения, явный null типа депозита отклоняется.
При переводе счёта в bank/cash депозитные параметры очищаются. Аудит использует прежний
механизм account updated; изменение справочных полей не корректирует начальный остаток.

## 9. Прогноз и движения депозитов

Прогноз читает текущий balance_minor и дату as_of из серверного snapshot. Формула:
остаток × годовая ставка / 100 × фактические дни / 365. Ставка масштабируется до 4 знаков,
суммы считаются BigInt; округление half-up до minor unit выполняется один раз в конце.
Для депозита с окончанием используется его дата; накопительный без окончания предлагает
3/6/12 календарных месяцев с ограничением дня последним днём целевого месяца. Прошедший срок
даёт 0 будущих дней/дохода; отсутствие ставки/типа/необходимой даты даёт пояснение без расчёта.
Никакой капитализации, будущих движений, фиктивных начислений или изменения баланса.

Статистика использует неудалённые операции snapshot от opening_date до as_of: переводы
по каждой стороне отдельно и income только по category_id категории дохода с точным
названием «Проценты по депозиту», включая архивную. Это существующий явный способ обозначения
процентов. Обычный доход и текст комментария не являются признаком процентов. Смена/переименование
категории пересчитывает классификацию; это пояснено в UI. Остальные доходы/расходы могут влиять
на фактический остаток, поэтому приведённые движения не выдаются за полную сверку баланса.
Расчёт не хранится отдельно и обновляется по актуальному snapshot после изменений операций.

## 10. История остатка, сроки и сравнение

Период графика/изменения остатка — последние 3/6/12 календарных месяцев, включая текущий.
Точки: остаток на конец завершённых месяцев, последняя — на as_of из snapshot. Начальный
остаток включается с opening_date; более ранние месяцы имеют ноль. Все реальные доходы,
расходы и обе стороны переводов учитываются с правильным знаком, прогнозы не включаются.
Изменение за период = последний остаток − остаток непосредственно перед первым днём периода.
Поэтому начальный остаток входит в изменение, если учёт начался внутри периода (UI поясняет).
Деньги вычисляются BigInt; в Number переводятся только нормализованные координаты SVG.

Сравнение включает все депозиты, в том числе архивные, группирует KZT/USD/EUR без суммирования.
Пополнения/снятия — суммы переводов за весь срок учёта до as_of, изменение — за выбранный
период. Операции индексируются по счетам один раз; отдельного хранилища истории нет.
Окончание вычисляется по текущей календарной дате устройства при отрисовке: день окончания
ещё считается «Скоро заканчивается» (0 дней), следующий день — «Срок истёк».


## 2026-11-06 — Цели накопления и месячные планы (локально)

- Миграция `0006_savings` следует за `0005_deposit`: `savings_goals`, `goal_allocations`, `deposit_plan_versions`. Ledger не изменяется, автоматических операций нет. Все таблицы под FORCE RLS; составные FK включают владельца и валюту. Новые права runtime включены в `scripts/grant-runtime.sql`.
- Распределения — точные целые минимальные денежные единицы. Один счёт может финансировать несколько целей. Перед увеличением суммы проверяется совокупное распределение против положительного текущего остатка. Используется существующая блокировка строки пользователя, общая с финансовыми изменениями; параллельные запросы не могут распределить одни деньги дважды.
- Снятие, изменение начального остатка или операции не меняет выделенные суммы. Возникающий дефицит показывается отдельно; уменьшение старого распределения разрешено даже при частичном исправлении дефицита. Архивный счёт допускает только сохранение/уменьшение прежнего распределения. Можно убрать его и выбрать другой счёт.
- Ручной и привязанный прогресс взаимоисключающие. Ручная сумма никогда не входит в балансы. Валюта созданной цели неизменна. Ежемесячный ориентир: остаток / число календарных месяцев, включая текущий и целевой; округление вверх. Просроченная дата не даёт месячного расчёта.
- Завершение требует достигнутой цели без дефицита на её счетах и сохраняет распределения. Архивация явно освобождает их, сохраняет снимок прогресса и аудит прежних распределений. При восстановлении привязанной цели распределения назначаются заново; ручной прогресс сохраняется.
- План депозита хранится по месяцу вступления в силу в часовом поясе пользователя. Изменение/отключение меняет только текущий месяц; прежняя сумма переносится на следующие месяцы до нового изменения. Исторические планы неизменны, факты пересчитываются по актуальным входящим переводам. Доходы, начальный баланс, распределения и будущие операции исключены. Процент ограничен 100%, превышение видно в фактической сумме.
- Счёт с распределениями или историей плана нельзя удалить (предлагается архив). Депозит с историей плана нельзя преобразовать в другой тип, чтобы сохранить доступ к истории. Архивный депозит позволяет отключить план.
- API: GET `/finance/savings`; POST `/finance/goals`; PUT `/finance/goals/{id}`; POST `/finance/goals/{id}/status`; GET/PUT `/finance/deposit-plans/{id}`. Изменения защищены существующими сессией, CSRF, version/revision и аудитом. Пользователь не передаёт user_id.
- UI: «Цели» рядом со счетами и категориями; планы внутри деталей депозита. Деморежим не изменён. При неудаче обновления после сохранения интерфейс не предлагает повторно создать уже сохранённую запись.


## 2026-11-13 — Kaspi import / 0007_kaspi

- Единый ledger сохранён. Новые tenant-таблицы: `import_batches`, `import_movements`, `bank_bindings`, `import_rules`; FORCE RLS и составные FK по владельцу. Сохранение сериализуется существующей блокировкой пользователя; уникальность банковского движения обеспечивается БД. Preview сверяется с хешем версий счетов, операций, правил и import evidence перед commit.
- Идентификатор банковского счёта: SHA-256 исходного реквизита, затем SHA-256 с UUID владельца и именем банка. Полный реквизит не сохраняется; счёт выбирается явно, затем запоминается привязка. Новый счёт автоматически не создаётся.
- Дедупликация: банк/счёт + дата + точная сумма + тип + полное нормализованное описание/дополнительные сведения + порядковый номер одинакового движения. Одинаковые реальные строки сохраняются отдельно; повторные наблюдения связываются с прежними записями. Дополнительные одинаковые строки и потенциальные совпадения с ручными операциями требуют решения. Пропущенные строки можно импортировать позже. Удалённые/отредактированные пользователем операции не восстанавливаются и не перезаписываются повторной загрузкой.
- Продавец сопоставляется по полному нормализованному имени, без частичных совпадений. Правила категории/собственного счёта сохраняются только по явному выбору. Номер собственной карты не зашит в приложение. Внешние исходящие переводы — расходы «Переводы людям»; неизвестные покупки и входящие поступления требуют проверки. Недостающая предложенная категория создаётся только при commit с проверкой существующих названий.
- Внутренний перевод остаётся одной существующей транзакцией с двумя счетами. Механизм сопоставления допускает привязку входящей стороны другого банка к этой же записи; парсер другого банка не реализован. Сопоставление не меняет тип, категорию и второй счёт прежней операции.
- Возвраты/отмены/FX/возврат собственных средств: `transactions.adjustment_type` и необязательный `related_transaction_id`. Направление денежного движения хранится прежними source/destination полями. Корректировки меняют остаток. С 16.11.2026 подтверждённые возвраты/отмены расхода уменьшают чистые расходы исходной категории в дату возврата; FX и неподтверждённые корректировки исключены из доходов/расходов. Все корректировки видны отдельно в истории. Исходная операция связывается автоматически только при единственном точном совпадении продавца и противоположной суммы либо явно пользователем. Комиссия остаётся расходом.
- Начальный остаток не меняется молча. Импорт до даты начала учёта блокируется до исключения строк или явного согласования новой даты/остатка. Preview показывает конечный расчётный остаток и расхождение. Расхождение требует отдельного подтверждения и не порождает фиктивную операцию.
- Отмена мягко удаляет только созданные этим импортом операции; сопоставленные старые операции сохраняются. Версии, последующие импорты, платежи и внешние корректировки защищены: зависимая отмена блокируется. Изменение начала учёта можно откатить атомарно, если оно не затронет последующие активные записи. Guard начального остатка по-прежнему требует версию, аудит и не допускает исключения действующих движений; tombstone отменённого импорта больше не мешает восстановить прежнюю дату. Граница для создания/изменения действующей операции не ослаблена.
- Новых облачных сервисов, OCR, ИИ и банковских API нет. Ограничения: только проверенный текстовый Kaspi Gold/KZT; неоднозначные строки требуют ручного решения; полноценная визуальная приёмка и реальный пользовательский импорт ещё не выполнены. Исходная реальная выписка проверена парсером, но не внесена в личную базу.


## 2026-11-16 — адресная проверка корректности Kaspi

- Без новой миграции: `expense_correction_minor`, `correction_category_id` и `adjustment_pending` вычисляются при сериализации существующих операций. Положительный связанный refund/reversal/return_funds уменьшает расход исходной категории, не доход; дата движения и фактические остатки не меняются. FX остаётся отдельным изменением остатка, не обычным доходом и не фиктивным расходом.
- Проверка связей и невозвращённой части общая для ручного API и импорта, внутри существующей сериализованной транзакции пользователя. Перепривязка к чужому пользователю, цепочки корректировок, неправильный счёт/дата, превышение исходного расхода отвергаются. Уменьшение/перенос исходного расхода проверяет зависимые возвраты; удалить его можно после снятия связей/удаления возвратов. Смена категории отражается в возврате автоматически.
- Автосвязь только с единственным обычным расходом того же продавца и противоположной точной суммы, при достаточном остатке. Частичный возврат связывается явно. Неоднозначные/превышающие остаток строки сохраняются только после проверки как отдельные неподтверждённые корректировки; произвольная категория расхода не назначается. В существующем редакторе можно уточнить или снять связь.
- Отмена своего перевода проводится существующей операцией обратного перевода между двумя счетами после явного выбора/подтверждённой привязки. Односторонняя корректировка со ссылкой на внутренний перевод запрещена; отдельная система отмен/начислений не добавлялась.
- Повторные одинаковые строки требуют проверки даже для известного продавца. Fingerprint+ordinal и сопоставление двух банковских сторон сохранены. Ручные категории не перезаписываются.
- История, сводки, категории, график и drilldown используют одинаковую проекцию чистых расходов. Отрицательные категории видны точными суммами; доли/сектора рассчитываются только от положительных категорий, общий итог включает отрицательные. Для неположительного предыдущего итога процентное сравнение не выводится. График допускает отрицательные чистые расходы.
